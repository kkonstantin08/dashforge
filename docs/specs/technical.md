# DashForge · техническая спецификация

Спецификация этапа B, утверждена 19 ноября 2026 года. Сценарии, размеры и критерии приёмки описаны в [продуктовой спецификации](product-and-design.md). Путь реализации описан в [плане](../plans/mvp.md).

## Стек и границы

- Одна клиентская Angular SPA, standalone, TypeScript strict и strictTemplates, OnPush, zoneless по умолчанию. На дату спецификации стабилен Angular core 22.3.0, CDK 22.3.0 и Angular CLI 22.2.8. Проверить актуальные stable-теги и совместимость при старте C. Предлагаемая ветка Node.js — 24 LTS от 24.15.0. Локальный Node.js 20.20.2 с Angular 22 несовместим. Приложение и CI используют одну совместимую ветку и lockfile. [Совместимость Angular](https://angular.dev/reference/versions) · [Zoneless](https://angular.dev/guide/zoneless)
- Signals и `computed` для UI и локального состояния. RxJS 7.x используется для события движения Angular CDK, подписка живёт в пределах жеста. Angular Reactive Forms используются в диалогах с несколькими полями. Для заметки достаточно textarea и события input. [Angular Drag and Drop](https://angular.dev/guide/drag-drop)
- CSS Grid, нативный IndexedDB, Angular TestBed/Vitest, Playwright, ESLint, Prettier и GitHub Actions. Нативному IndexedDB достаточно одного хранилища, поэтому Dexie пока не нужен. Angular Router, NgRx, Angular Material, SSR и отдельный движок виджетов не входят в MVP.
- Для статической публикации предложен GitHub Pages с учётом base path репозитория. E2E работает со сборкой на localhost. Для обычных тестов своего приложения штатные браузеры Playwright проще и достаточно надёжны. CloakBrowser — опция при изменении требований. При подготовке браузерной автоматизации повторно проверить глобальную политику.
- Экспорт и синхронизация между устройствами за пределами MVP. Данные остаются в origin браузера. При изменении origin или очистке данных сайта хранилище меняется или очищается. Использовать один постоянный URL для опубликованного приложения.

## Структура и контракты

| Область | Ответственность |
|---|---|
| `src/app/app.ts` | Запуск, заголовок, темы, состояния загрузки и сохранения. |
| `src/app/dashboard/dashboard.ts` | Отрисовка сетки, каталог, выбор карточки, переход в редактор и сброс. |
| `dashboard/widget-card.ts`, `dashboard/widget-inspector.ts` | Оболочка карточки, ручки, динамический вывод содержимого и настройка выбранного виджета. Открытие инспектора поверх доски не меняет размеры сетки. |
| `dashboard/dashboard-store.ts` | Источник состояния рабочего пространства. Публичные команды проверяют изменения и передают снимки в хранилище. Эфемерные UI-состояния остаются в компоненте. |
| `dashboard/layout.ts` | Чистые функции границ, пересечений, размещения, проекции и сброса. |
| `dashboard/grid-gesture.ts` | Привязка Angular CDK к CSS Grid и resize на Pointer Events. Общий расчёт кандидата и единственный commit. |
| `src/app/widgets/` | Конечный реестр метаданных и lazy-компонентов, типизированные настройки, четыре реализации. |
| `src/app/storage/indexed-db.ts` | Чтение и транзакционная запись одного снимка, проверка версии, обработка ошибок. |

`Placement = { col: number, row: number, width: number, height: number }` содержит целочисленные индексы от нуля. UI отображает индексы от единицы. Пересечение вычисляется на полуоткрытых интервалах. Конечная строка и колонка могут совпадать с правой или нижней границей. Хранить `Workspace = { theme, widgets, desktop, mobile? }`. `widgets` — список объектов с `id`, `type` и типизированными данными по `type`. `desktop` и существующий `mobile` содержат по одной позиции на ID. UUID выдаёт `crypto.randomUUID()`. При одинаковых координатах при сортировке используется порядок исходного списка.

`validatePlacement(candidate, occupied, limits)` возвращает `'ok' | 'bounds' | 'size' | 'collision'`. `occupied` содержит остальных виджетов. `firstFree(size, occupied, bounds)` возвращает первую позицию или `null`. `projectMobile(workspace)` возвращает позиции всех виджетов в четырёх колонках с высотами из продуктовой спецификации. Любая команда должна сохранить возможность показать все виджеты на узком экране. Если проекция или явный узкий макет не вмещает новую карточку, добавить её целиком нельзя. При удалении позиции из обеих раскладок и данные виджета уходят одной операцией. `resetLayout(workspace)` находит позиции для всех экземпляров до изменения состояния. Сохранить старый макет и сообщить об ошибке, если валидный новый набор позиций не найден.

`DashboardStore` предоставляет readonly Signals `workspace` и `saveState`, а также команды `load()`, `add(type)`, `remove(id)`, `place(id, view, rect)`, `updateWidget(widget)`, `setTheme(theme)`, `resetLayout()` и `retrySave()`. Команды с отказом возвращают результат для UI, а не исключение из пользовательского жеста. Дочерние компоненты получают стабильные входные объекты, в цикле используется `track widget.id`. Изменение заметки не клонирует модели остальных карточек и не обновляет события календаря.

## Жесты и панель

- Перенос использует `CdkDrag` с `CdkDragHandle`. Программная подписка на движение обновляет один DOM-контур через `requestAnimationFrame`. Шаблонный обработчик каждого пикселя не нужен. При старте сохраняются размеры сетки и смещение указателя относительно карточки. Для координат учитывать прокрутку и текущий прямоугольник сетки. При завершении очистить CDK transform, затем синхронно применить результат по координатам CSS Grid.
- Resize регистрирует Pointer Events на отдельной ручке. Использует `setPointerCapture`, доступную ширину сетки и общий перевод пикселей в ячейки. Drag и resize взаимно исключаются. `pointercancel`, потеря захвата, Escape, смена ширины сетки, удаление карточки и уничтожение компонента очищают контур, кадр, listeners и подписки. При несовместимой ширине и столкновении выполняется откат.
- Снимок рабочего пространства меняется максимум один раз на успешный жест, включая результат из инспектора. Для клавиатуры использовать явные поля координат и размеров с одним `Apply`. На сенсорном устройстве ручки доступны в редакторе, прокрутка блокируется только на самой ручке во время жеста.
- Компоненты четырёх виджетов загружать через типизированный реестр и динамические импорты по встреченному типу. Начальная оболочка и сигналы состояния загружаются сразу. Динамический импорт оплачивается один раз на тип. После baseline сравнить суммарный JS с вариантами разделения, особенно для стартового набора из всех четырёх типов. [Angular Deferred Loading](https://angular.dev/guide/templates/defer)

## Хранение

`IndexedDbWorkspace.read(): Promise<StoredWorkspace | null>` читает объект с ключом `workspace`. `write(workspace, expectedRevision): Promise<number>` проверяет ожидаемую ревизию и пишет снимок в одной readwrite-транзакции. Схема записи `{ schemaVersion: 1, revision: number, workspace }`. Отсутствующая запись означает первый запуск и ожидаемую ревизию 0. Снимок валидируется по схеме, ID, типам и геометрии. Сохранение считается завершённым только на `transaction.complete`. Ошибки доступа, блокировки, квоты и неверной схемы отображаются через состояния UI. Открытые соединения закрываются при `versionchange` и очищаются при завершении владельца. [IndexedDB](https://w3c.github.io/IndexedDB/)

Геометрия, настройки, удаление и тема идут на запись сразу. При вводе текста ждать 250 мс тишины, на blur запрашивать сохранение сразу. Только одна запись в работе. Пока она идёт, хранить последний актуальный снимок, включая изменения настройки и текста вместе. Успешный commit предыдущего снимка не переводит индикатор в `Saved`, пока есть следующая правка. После временной ошибки повтор сохраняет последний снимок. Устаревшая вкладка останавливает запись и предлагает перечитать сохранённый макет с подтверждением потери локальных несохранённых изменений. После `Saved` снимок переживает обычную перезагрузку. При резком закрытии вкладки до commit запись не гарантируется.

## Особенности виджетов

- **Clock.** Один общий источник минутного времени. Один таймер по границе минуты нужен только при наличии Clock и видимой вкладке, после пробуждения обновить сразу. Кешировать `Intl.DateTimeFormat` на экземпляр и набор настроек. Проверять IANA-пояс и переключение даты при смене пояса.
- **Bookmarks.** Валидировать через URL и разрешать только `http:`/`https:`. Открывать с `target="_blank"` и `rel="noopener noreferrer"`. Данные рендерятся как текст. Использовать локальные иконки, чтобы не запрашивать favicon и не раскрывать историю адресов внешней службе.
- **Notes.** Простой текст, стабильный ID каждой заметки. Ввод сразу обновляет модель и использует общую очередь записи. Никакой HTML-вставки.
- **Calendar.** Локальные даты хранятся как `YYYY-MM-DD`, время как опциональная строка `HH:mm`. Месяц строится по частям даты, включая переход года и високосный февраль. События текущего дня с указанным временем учитываются до конца этой минуты, события без времени до конца дня. При равных датах сортировать события с временем по времени, затем без времени, затем по ID. Пересчитывать список при открытии, изменении и возврате к вкладке. Для видимого документа каждый Calendar планирует однократный timeout на ближайшее истечение события или местную полночь, в зависимости от того, что наступит раньше. При скрытии вкладки или уничтожении виджета timeout снимается.

## Проверки и baseline

1. Unit и TestBed проверяют состояние сетки, события со сроками, таймер, модель, доступность основных контролов и ошибки записи. В настоящем браузере проверяются IndexedDB и сценарии пользователя.
2. E2E запускаются Playwright через production build. Chromium покрывает мышь, клавиатуру, IndexedDB, сенсорный drag и resize через браузерный ввод. WebKit проверяет мобильную вёрстку и сценарий сохранения. Эмуляция и реальный телефон отражаются отдельно в отчёте. [Playwright Emulation](https://playwright.dev/docs/emulation)
3. До выставления budgets снять baseline для холодной первоначальной загрузки, открытия обычного макета, 5/10/20 виджетов и повторного открытия из IndexedDB. Использовать синтетические данные и минимум пять прогонов каждого профиля, привести медиану и диапазон. Фиксировать версию браузера, устройство, build, viewport, cache/CPU условия и состав виджетов. Измерять initial JS и CSS в raw и gzip, время navigation → первая готовая сетка, время чтения и записи снимка, renderer CPU и heap после загрузки и взаимодействия, long tasks и обновления компонентов.
4. Для нагрузки повторить не менее 20 успешных переносов подряд и 20 resize на макете с 20 виджетами, зафиксировать кадры, задержку и число сохранений. Повторить открытие/закрытие редактора, добавление/удаление часов и перезагрузки, проверить освобождение подписок, Pointer Events и таймеров. Отдельно сверить обновления `Dashboard` и неизменённых карточек через временную dev-инструментацию. Продакшен-метрики и число компонентных проверок относятся к своим сборкам.
5. Зафиксировать методику и результаты в `docs/performance.md`. После первого измерения установить budgets в Angular и/или CI исходя из baseline. Указать наблюдаемую деградацию и ограничения замеров. До замеров заявлять только архитектурные цели.
